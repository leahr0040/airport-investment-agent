Section 2 — the scoring methodology, in five subsections:

2.1 Weights. Present `SCORING_WEIGHTS` as a table: volume 1/3, headroom 1/3, delay frequency 1/3.
Then the part the code cannot show — the weights are equal because no labeled outcome data exists
to fit them against, and a visible, inspectable weight table is the deliberate substitute for
statistical justification. Name the file and export (`src/domain/scoring/expansionScore.ts`,
`SCORING_WEIGHTS`) so a reader can check the table against the code.

2.2 The three components. One row per component naming the KPI, the function that computes it, and
its input: volume is `passengerMovements` from `computeVolumeKpi` over OpenSky movements; headroom
is `movementsPerRunway` from `computeHeadroomKpi`, total movements divided by runway count from the
FAA facility record; delay frequency is `eventCount` from `computeDelayKpi` over active FAA NAS
Status events. State the zero-runway case accurately: a facility reporting no runways resolves
headroom to no-data rather than dividing by zero, so that airport is scored on its remaining
components instead of being given a fabricated ratio.

2.3 Cargo separation. `isCargoCallsign` matches a trimmed, uppercased callsign against
`CARGO_CALLSIGN_PREFIXES` (list all ten: FDX, UPS, GTI, CKS, ABX, PAC, CLX, ACA, DAL, AAL), and a
null callsign is never classified as cargo. State why this matters — a cargo-dominated airport must
not be read as passenger demand — and state the honesty caveat: this is a movement-count proxy
classified by callsign prefix, not a measured passenger or cargo volume, and the prefix list is
itself a judgment call that will misclassify a passenger flight operated under a listed carrier's
prefix.

2.4 Normalization. `minMaxNormalize` scales each component to 0-100 across the airports in the
current query, not against any fixed or global reference range. Give it the two consequences it
deserves: scores are comparative rather than absolute, so the same airport can score differently
depending on what else is in the comparison set; and a single-airport query normalizes every
available component to 50, because minimum equals maximum. Both belong in the document as
disclosures, not footnotes.

2.5 When a source is unavailable. Each component resolves independently to a KPI or to a failure
reason, and the weight per surviving component becomes one divided by the number of components that
resolved — not a fixed third with a zero contribution for the missing one. Every result carries a
coverage string, and an airport with no surviving component scores 0 with the coverage string
`0 of 3 components available`. Also state the deliberate distinction: an empty OpenSky window is a
measured zero, not a failure, so a zero-traffic airport keeps all three components and ranks last
rather than being excluded.
