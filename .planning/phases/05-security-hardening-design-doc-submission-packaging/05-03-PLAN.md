Section 5 — key tradeoffs. A table or a short list, each entry naming the choice, what was given up,
and why the trade was worth it. Include at least these six:

- Live public APIs with no bulk download. Bought: every figure is current and fetched, nothing is a
  stale snapshot. Cost: no keyless live API publishes per-airport passenger volumes, so the volume
  KPI is a movement-count proxy classified by callsign prefix, and the document says so everywhere
  it appears rather than once.
- Equal weights instead of fitted ones. Bought: an inspectable weight table anyone can argue with.
  Cost: no statistical justification, because no labeled outcome data exists to fit against.
- Min-max normalization across the query set. Bought: a spread that is meaningful for the airports
  actually being compared. Cost: scores are comparative, not absolute; cross-reference section 2.4.
- In-memory cache and in-memory rate limiter. Bought: no database, no Redis, nothing for a reviewer to
  install; the demo runs from `npm install` and a key. Cost: state dies with the process and there is
  no cross-instance correctness — which this deployment does not need, since it is one process.
- Natural-language resolution moved to the LLM. Bought: a chat that understands phrasings a lookup
  table never would. Cost: the registry-backed resolver and its ambiguity metadata were deleted in
  the 2026-08-13 pivot under the one-day budget, leaving a hardcoded region table as the only
  code-level resolution; be specific about what was lost.
- Per-source failure isolation instead of all-or-nothing. Bought: one upstream outage degrades one
  component rather than the whole answer. Cost: two answers to the same question can rest on
  different component sets, which is why every result carries a coverage string.

Section 6 — where AI is used. Two subsections, kept explicitly separate per D-08:
`### 6.1 AI in the product` and `### 6.2 AI in building this project`.

6.1 must establish the boundary in both directions. What the model does: parses intent, chooses
among the four tools `resolve_region`, `score_airports`, `flight_destinations`, and
`runway_conditions`, and narrates the results — inside a loop capped at three tool rounds. What it
is forbidden to do: `SYSTEM_PROMPT` in `src/adapters/llm/google.ts` instructs it never to invent
scores, KPI numbers, or airport data, to state only numbers that came from a tool result, and to
state the data window and the measured-versus-proxied label on any airport-specific answer. Name the
structural guarantee behind that: numbers rendered in the UI come from structured tool output and
are never parsed out of the model's prose.

Then the part that transparency requires — the two judgments the model genuinely makes itself,
because no code computes them. There is no great-circle distance function anywhere in the codebase,
so the long-haul distance threshold and the classification of each destination are the model's own
estimate, which the prompt requires it to state and label as its own. There is no runway-separation
or parallel-runway detection either, so any judgment about runway configuration is likewise the
model's own estimate over real runway endpoint coordinates and real delay events, and is likewise
required to be labeled. Say plainly that these were deliberate scope decisions made in Phase 4, not
oversights, and that the mitigation for them is disclosure rather than silence. Close with one
sentence cross-referencing section 4.4: text from third-party APIs enters the model's context as
data, never as instructions.

6.2 is short — two or three sentences. The codebase was written with Claude Code under a
plan-and-execute workflow, with a phase's context, research, plan, and summary written before its
code. State it plainly; for a forward-deployed-engineer submission, disclosure reads better than
omission. Write it so it remains true and complete whether or not the `.planning/` directory is
included in the submitted repository: do not instruct the reader to open a file under `.planning/`,
because whether that directory ships is still an open decision (Task 3).
