<objective>
Build the graded core: a pure, zero-I/O, zero-LLM TypeScript function that turns per-airport KPIs (OpenSky movements, FAA facility/runway data, FAA NAS status) into an Expansion Opportunity Score, with an inspectable component breakdown, a single-file weights/normalization declaration (SCORE-03), cargo/passenger separation (SCORE-04), and deterministic fixture-based tests (SCORE-05).

Purpose: this is the non-negotiable deliverable the project grades directly. Every other phase either feeds this function (Phase 2's adapters, plan 03-01's FAA facility adapter) or consumes its output (Phase 4's chat/tool-calling layer). It must be provable correct by `npm test` alone, independent of any live credential or network state.

Output: `scoreAirports(inputs)` returning an `ExpansionScore[]`, exported from one file alongside its weights table, cargo-carrier allowlist, and normalization function — fully unit-tested against fixed, hand-computed fixtures with no network access anywhere in the test suite.

Formula, locked by CONTEXT.md D-02/D-03/D-04: three equally-weighted KPI groups — traffic volume (passenger movements, cargo excluded per SCORE-04), capacity headroom (all movements per runway), and delay/closure frequency (FAA NAS event count) — each min-max normalized to 0–100 across the compared set, averaged. A HIGH score means demand is outpacing capacity (D-03). When a group is unavailable for an airport, its weight is redistributed equally across the remaining available groups for that airport (Claude's Discretion in CONTEXT.md, mirroring Phase 2 D-06's per-source degradation philosophy). Per D-05, long-haul flight share (great-circle distance) is deliberately NOT a fourth group and does not appear anywhere in this module — it stays a separate, on-demand metric answered directly in Phase 4, out of this plan's scope entirely.
</objective>

**Cargo-carrier allowlist** — declare exactly this array, with the confidence-caveat comment carried verbatim from RESEARCH.md's Assumption A5 (do not treat this as a further user-decision gate; CONTEXT.md's Claude's Discretion section already resolved it):
`export const CARGO_CALLSIGN_PREFIXES = ['FDX', 'UPS', 'GTI', 'CKS', 'ABX', 'PAC', 'CLX', 'ACA', 'DAL', 'AAL'] as const;`
Comment: this list is curated (RESEARCH.md, general aviation knowledge, carrier-code lookups), not exhaustive — smaller regional freighter operators are omitted, and `DAL`/`AAL` specifically also cover passenger-carrier flights (Delta/American operate both), so a `DAL`- or `AAL`-callsigned movement is classified as cargo under this heuristic even when it may be a passenger flight. Accepted per CONTEXT.md as a disclosed, documented assumption, not a further decision gate.

`isCargoCallsign(callsign: string | null): boolean` — `false` for `null`; otherwise trim and uppercase the value and check `CARGO_CALLSIGN_PREFIXES.some(p => upper.startsWith(p))`.

**KPI types and compute functions:**
- `VolumeKpi = { passengerMovements: number; cargoMovements: number; totalMovements: number }`. `computeVolumeKpi(movements: Movements): VolumeKpi` — concatenate `movements.departures` and `movements.arrivals`, count cargo via `isCargoCallsign` on each `callsign`, `passengerMovements = totalMovements - cargoMovements`.
- `HeadroomKpi = { movementsPerRunway: number; runwayCount: number; totalMovements: number }`. `computeHeadroomKpi(movements: Movements, facility: FaaFacility): HeadroomKpi` — `totalMovements = movements.departureCount + movements.arrivalCount` (ALL movements, cargo included — a cargo aircraft occupies a runway slot the same as a passenger one), `runwayCount = facility.runways.length`, `movementsPerRunway = totalMovements / Math.max(1, runwayCount)`.
- `DelayKpi = { eventCount: number }`. `computeDelayKpi(nasStatus: NasStatus): DelayKpi` — `{ eventCount: nasStatus.events.length }`.

`minMaxNormalize(value: number, dataset: number[]): number` — `min`/`max` via `Math.min(...dataset)`/`Math.max(...dataset)`; if `max === min` return `50` (avoids a division by zero when every airport in the compared set ties on this KPI — a genuine tie, not a defect); else `((value - min) / (max - min)) * 100`.

**Weights, declared in this same file (SCORE-03 — one inspectable place for weights AND normalization AND the cargo list, all in this one module):**
`export const SCORING_WEIGHTS = { volume: 1 / 3, headroom: 1 / 3, delayFrequency: 1 / 3 } as const;`
Comment: D-04 — equal weights by design (no labeled outcome data exists to fit against); disclosed, not data-fitted. When a component is unavailable for an airport its weight is redistributed equally across that airport's remaining available components rather than zero-filling or dropping the airport (see `scoreAirports` below).

**Component and score types:**
```
ComponentResult<T> =
  | { available: true; kpi: T; normalized: number; contribution: number }
  | { available: false; kpi: null; normalized: null; contribution: null; reason: AdapterFailReason }

ScoringComponentBreakdown = {
  volume: ComponentResult<VolumeKpi>;
  headroom: ComponentResult<HeadroomKpi>;
  delayFrequency: ComponentResult<DelayKpi>;
  weightPerComponent: number;
  availableComponentCount: number;
  coverage: string; // e.g. "2 of 3 components available"
}

ExpansionScore = { icao: string; score: number; components: ScoringComponentBreakdown }

ScoringInput = {
  icao: string;
  movements: AdapterResult<Movements>;
  facility: AdapterResult<FaaFacility>;
  nasStatus: AdapterResult<NasStatus>;
}
```
(Write these as real TypeScript type declarations, not a fenced pseudo-code block — the shapes above are the literal contract.)

**`scoreAirports(inputs: ScoringInput[]): ExpansionScore[]`:**
1. For each input, compute per-group availability: `volume` is available iff `input.movements.ok`, using `computeVolumeKpi(input.movements.data)`. `headroom` is available iff BOTH `input.movements.ok` AND `input.facility.ok`, using `computeHeadroomKpi(input.movements.data, input.facility.data)`; its unavailable `reason` is `input.movements.ok ? input.facility.reason : input.movements.reason` (movements failure takes precedence when both fail, since it is checked first). `delayFrequency` is available iff `input.nasStatus.ok`, using `computeDelayKpi(input.nasStatus.data)`.
2. Build one normalization dataset PER GROUP, containing only the values from airports where that specific group is available (per case group 3 in Task 1's tests: an airport missing headroom must not appear in the headroom dataset, but still appears in the volume/delay datasets if those are available for it).
3. For each airport, normalize each of its available groups against that group's dataset via `minMaxNormalize`; count `availableComponentCount`; set `weightPerComponent = availableComponentCount > 0 ? 1 / availableComponentCount : 0`; set each available component's `contribution = normalized * weightPerComponent`; set `score = ` the sum of all available contributions (equivalently, the sum of available normalized values divided by `availableComponentCount`) — if `availableComponentCount` is `0`, `score = 0`.
4. Build `coverage` as `` `${availableComponentCount} of 3 components available` ``.
5. Return one `ExpansionScore` per input, in the same order as `inputs`.

The function must not call `Date.now()`, `Math.random()`, or read any mutable module-level state — every value in the output must be a pure function of `inputs`, which is what makes the determinism case in Task 1 pass.
