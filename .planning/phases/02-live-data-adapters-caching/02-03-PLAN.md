Create `src/domain/adapters/opensky.ts`.

Module conventions: `import "server-only"` as the first line, exactly as `src/config/env.ts` does. Read `OPENSKY_CLIENT_ID` and `OPENSKY_CLIENT_SECRET` only through `getEnv()` imported from `@/config/env` — never from `process.env` directly. Emit no log output of any kind from this module: not the token, not the client secret, not a response body. RESEARCH.md Pitfall 5 is explicit that the convenient debugging habit here is the leak.

Constants: the token endpoint `https://auth.opensky-network.org/auth/realms/opensky-network/protocol/openid-connect/token` and the flights base `https://opensky-network.org/api` as module-level string literals. Both are fixed — no part of either is ever built from an argument.

Exported types:
- `FlightMovement` — `icao24: string`, `callsign: string | null`, `firstSeen: number`, `lastSeen: number`, `estDepartureAirport: string | null`, `estArrivalAirport: string | null`, `departureAirportCandidatesCount: number | null`, `arrivalAirportCandidatesCount: number | null`. The two nullable airport fields and the two candidate-count fields are carried forward deliberately: OpenSky infers origin/destination from ADS-B proximity rather than a flight plan, so both the null case and the ambiguity signal are real data Phase 3 may want (RESEARCH.md Open Question 2). Carrying them now costs nothing; re-fetching later costs a quota round trip.
- `Movements` — `icao: string`; `window: { begin: number; end: number; beginIso: string; endIso: string }`; `departures: FlightMovement[]`; `arrivals: FlightMovement[]`; `departureCount: number`; `arrivalCount: number`; `unknownDestinationCount: number`; `unknownOriginCount: number`. The ISO strings exist so Phase 4 can state the data window in prose (QUERY-05) without recomputing it from Unix seconds.

Exported functions:
- `clearTokenCache(): void` — resets the module-level token state. It exists as a test seam and is used by the 401 recovery path; one short comment saying so is enough.
- `fetchMovements(icao: string): Promise<AdapterResult<Movements>>`.

`fetchMovements` behaviour, in order:
1. Call `isValidIcao(icao)` first, before anything else. On false, return ok false with reason `invalid_input` immediately — no token fetch, no URL construction, no network call at all. Add a one-line comment marking this as the injection gate for the value that is about to be interpolated into an outbound query string.
2. Wrap everything after that in a try/catch that never rethrows.
3. Compute the window: floor `Date.now() / 1000` to `OPENSKY_BUCKET_SECONDS` for `end`, and set `begin` to `end` minus 86400. Use the same floored values in the cache key and in both outbound URLs. RESEARCH.md Pitfall 1 is that computing these fresh on every call gives every request a unique cache key and silently defeats DATA-04.
4. Build the cache key from the adapter name, the validated code, and the window bounds.
5. Inside `withCache(key, OPENSKY_TTL_MS, ...)`: obtain the token, then issue both leg requests concurrently with `Promise.all`. Build each URL from the flights base plus the path segment for the departure or arrival endpoint, with the airport code passed through `encodeURIComponent` as defence in depth in case the format gate is ever loosened, plus the begin and end values. Pass `AbortSignal.timeout(3000)` on every request and set the Authorization header to the bearer token. No retry — D-07 is explicit.
6. Response handling per leg: HTTP 404 means the window held no matching flights, so treat that leg as an empty array rather than an error. HTTP 429 must surface as reason `rate_limited`. HTTP 401 or 403 must call `clearTokenCache()` so the next request re-authenticates, then surface as reason `error` — clearing the token is not a retry. Any other non-OK status surfaces as reason `error`. Use a small internal error type carrying the reason so the outer catch can map it, rather than parsing message strings.
7. If BOTH legs returned 404, return ok false with reason `no_data`. A single 404 leg is a legitimate zero for that leg.
8. Normalise each raw record into `FlightMovement`, coercing absent fields to null rather than dropping the record. Count `unknownDestinationCount` as departures whose `estArrivalAirport` is null, and `unknownOriginCount` as arrivals whose `estDepartureAirport` is null. Never filter a record out because an inferred airport was missing.
9. On success return ok true with the `Movements` object, `fetchedAt` as a fresh ISO-8601 timestamp, and `source` set to `opensky`.
10. In the catch: map an error whose `name` is `TimeoutError` to reason `timeout`, a carried reason to itself, and anything else to reason `error`. Populate `detail` with a short, non-secret string — the HTTP status or the error name only. Never place a response body, a header, the token, or the client secret in `detail`; the `AdapterResult` contract in `types.ts` states this and the tests assert it.

Token lifecycle (D-05, lazy): a module-level variable holding the token string and its absolute expiry in milliseconds. Before each use, return the cached token if its expiry is still in the future; otherwise POST form-encoded `grant_type`, `client_id`, and `client_secret` to the token endpoint with `AbortSignal.timeout(3000)`, read `access_token` and `expires_in` from the response, and store the expiry as now plus `expires_in` seconds minus a 30-second safety margin. No background timer, no interval, no proactive refresh.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → `fetchMovements(icao)` | The airport code originates from analyst text upstream and is untrusted until `isValidIcao` runs. It is then interpolated into an outbound URL — the one genuine injection surface in this phase. |
| adapter → OpenSky API | Server-to-server call carrying a bearer token derived from long-lived client credentials. |
| OpenSky response → app memory | Upstream JSON, including free-text `callsign` values, enters the cache and flows to later tiers unvalidated. |
| module scope → client bundle | The module reads credentials; if it were ever imported by a client component the secret boundary would collapse. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | `fetchMovements` outbound URL construction | high | mitigate | `isValidIcao` runs as the function's first statement, before the token fetch and before any URL is built; the test suite asserts zero fetch calls on rejection. `encodeURIComponent` wraps the code as defence in depth. Both upstream hosts are hardcoded literals with no user-influenced component. |
| T-02-02 | Information Disclosure | token lifecycle, `detail` field, module logging | high | mitigate | No log statements at all in the module (asserted by grep); `detail` carries only an HTTP status or an error name; tests assert the secret and token values never appear in `detail`. |
| T-02-03 | Information Disclosure | module reachable from a client bundle | high | mitigate | `import "server-only"` as the first line, matching `src/config/env.ts`; credentials read exclusively via `getEnv()`. |
| T-02-04 | Denial of Service | self-inflicted OpenSky quota exhaustion (4,000 credits/day, 4 credits per flights call) | medium | mitigate | Bucket-floored window timestamps make the cache key stable inside the TTL, so repeat requests cost zero credits; asserted by the three-fetch-call cache-hit test. |
| T-02-05 | Denial of Service | a hung upstream connection stalling the whole answer | medium | mitigate | `AbortSignal.timeout(3000)` on every request with no retry (D-07), so worst-case added latency from this source is bounded at 3 seconds and surfaces as a typed `timeout` failure. |
| T-02-09 | Spoofing | a stale or revoked token silently failing every request | medium | mitigate | 401/403 clears the cached token so the next request re-authenticates; the expiry margin is 30 seconds short of the issued lifetime so a token is never used at the edge of validity. |
| T-02-10 | Tampering | upstream free-text (`callsign`) staged for prompt injection in Phase 4 | medium | transfer | Out of scope here per SEC-04's Phase 4 assignment; mitigated at this layer by keeping `callsign` a plain typed string field on `FlightMovement` — never concatenated, rendered, or evaluated — so Phase 4 has a single isolated field to sanitise. |
</threat_model>
