<objective>
Make the app refuse to start when a required credential is absent, with an error that names the
variable and says where to get it, and ship the `.env.example` + README pair that lets a reviewer
go from `git clone` to a running app without reading source code.

Purpose: SETUP-01, SETUP-02 and SETUP-03. PROJECT.md removed the degraded/no-credential mode
entirely, which makes a vague startup failure the single worst outcome in the whole build — a
reviewer who cannot start the app scores the reasoning at zero. This plan is the mitigation.

Output: `src/config/env.schema.ts` + tests, `src/config/env.ts`, `src/instrumentation.ts`,
`.env.example`, and a rewritten `README.md`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OS environment → application config | Untrusted/incomplete environment values enter the process here; this is the only sanctioned entry point |
| server module graph → browser bundle | If the config module is reachable from a client component, all three credentials ship to the browser |
| working tree → git history | `.env.example` is committed by design; any real `.env` file must not be |
| process boot → first HTTP request | A boot that succeeds with an invalid config defers the failure into a request handler where it is far harder to diagnose |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-04 | Information Disclosure | `src/config/env.ts` reaching a client bundle | high | mitigate | Bare `server-only` import as the first statement of `env.ts` (V14). No `NEXT_PUBLIC_*` variable is defined anywhere in the schema, so no credential has a client-visible name. `env.schema.ts` deliberately holds no secrets — only names, defaults and help URLs — so it is safe even if imported broadly. |
| T-01-05 | Information Disclosure | scattered ambient-environment reads across modules | high | mitigate | Single-module read path enforced mechanically: the Task 1 verification counts ambient-environment reads under `src/**/*.ts` and fails on any hit outside `src/config/env.ts` and `src/instrumentation.ts` (the latter only inspects the Next.js runtime marker, never a credential). |
| T-01-06 | Denial of Service (self-inflicted) | boot sequence | high | mitigate | Validation is forced by `register()` in `src/instrumentation.ts`, which Next.js runs once per server instance and must complete before request serving. A top-of-file throw in a module nobody eagerly imports would not fire until some request happened to pull it in — that is the failure mode this hook exists to close. |
| T-01-07 | Information Disclosure | `.env.example` committed to the repository | medium | mitigate | Acceptance criteria require every value to be an obvious `your-...` placeholder and forbid realistic-looking token text; `.gitignore` (plan 01-01) still ignores every other `.env*` file. |
| T-01-08 | Information Disclosure | credential values echoed into the validation error message | medium | mitigate | The error builder emits only the variable NAME, a fixed help string, and the fixed remedy line — it never interpolates a received value, so a malformed secret cannot leak into logs or a terminal transcript. |
| T-01-09 | Spoofing | help URLs in `REQUIRED_ENV_HELP` / README pointing at a look-alike credential site | low | accept | URLs are fixed literals reviewed at planning time against RESEARCH.md and PROJECT.md; they are never constructed from input. Accepted at ASVS L1. |
</threat_model>
