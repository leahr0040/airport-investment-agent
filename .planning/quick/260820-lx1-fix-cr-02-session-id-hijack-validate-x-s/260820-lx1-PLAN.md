<objective>
Fix CR-02 from `.planning/phases/04-conversational-agent/04-REVIEW.md`: `src/app/api/chat/route.ts` and `src/lib/middleware/sessionRateLimitCheck.ts` each independently derive session identity as `req.headers.get('x-session-id') ?? req.headers.get('x-forwarded-for') ?? 'anon'` - an unauthenticated, client-chosen value used directly as both the rate-limit key and the lookup key into `sessionStore`'s in-memory conversation map. Any caller can set (or omit) `x-session-id` to read/continue another session's conversation, or collide multiple anonymous callers onto the shared key `'anon'`.

Purpose: per CLAUDE.md, "rate-limit the chat endpoint per session" and validate every user-supplied identifier at the trust boundary are both explicit, non-deferrable security requirements (SEC-03's per-session guarantee is meaningless if the session key itself is spoofable/collidable, which is exactly what CR-02 identifies). Fix it at the single point both consumers already pass through - `src/proxy.ts`, which runs for every `/api/chat` request before either `sessionRateLimitCheck.ts` or `route.ts`.

Output: `proxy.ts` validates `x-session-id` as a strict UUID via Zod's `z.uuid()` immediately after the (independent, unrelated) IP rate-limit check, returning a 400 `invalid_session_id` response for anything missing or malformed - no generated fallback is substituted. `sessionRateLimitCheck.ts` and `route.ts` are simplified to read the now-guaranteed-valid header directly, dropping their redundant fallback chains. Tests updated/added in all three files' test suites to cover the new 400 path and the removed fallback behavior.
</objective>
