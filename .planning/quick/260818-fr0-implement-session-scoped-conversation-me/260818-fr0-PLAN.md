<objective>
Give the chat agent session-scoped conversation memory: `POST /api/chat` already receives and rate-limits on an `x-session-id` header, but `runAgent` ignores it entirely and rebuilds a brand-new, empty Gemini `contents` array on every call. Wire the existing session id through to a per-session, TTL-bounded conversation store so repeated calls from the same session continue one conversation, using the `@google/genai` SDK's own `Chat` class instead of the current hand-rolled `contents` array + manual `thought_signature` echo - after live-verifying that `Chat`'s internal history capture actually covers what the manual code was specifically added to preserve.

Purpose: An analyst asking follow-up questions ("now compare that to Logan") currently gets an agent with no memory of the prior turn. This closes that gap with the smallest change that fits the existing single-process, no-persistent-DB constraints in CLAUDE.md.
Output: `src/adapters/llm/sessionStore.ts` (new, in-memory TTL-bounded session map), `src/adapters/llm/live.smoke.ts` (new, opt-in live proof of the `Chat` history claim), reworked `runAgent(sessionId, query)` in `google.ts`, `route.ts` wired to pass its session id through, and matching test coverage.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| client -> POST /api/chat (`x-session-id` header) | Previously only selected a rate-limit bucket (low stakes: worst case is a misattributed quota). Now it also selects which stored `Chat`/conversation a request reads and appends to - a new, higher-stakes use of the same unauthenticated, client-supplied value. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-quick-01 | Spoofing / Information Disclosure | `sessionStore.getOrCreateChat` (keyed by client-asserted `x-session-id`, no auth) | low | accept | No auth system exists anywhere in this project's scope (CLAUDE.md defers it). Conversation content is limited to public aviation data - airport codes, region names, and computed scores - never PII or secrets, so a guessed/reused session id exposes no sensitive data, only another analyst's query history for the TTL window. Same trust level the header already had for rate-limiting today; adding real auth is out of scope for a 24-hour demo build. |
| T-quick-02 | Denial of Service | `sessionStore.ts`'s `Map` (unbounded distinct session ids, each minting a new `Chat`) | low | accept | Sliding TTL eviction bounds any single session's memory lifetime (the documented `ponytail:` ceiling on `sessionStore.ts`). Bounding total `Map` size or requiring auth to mint a session would fully close this, but is out of scope at this project's single-process, demo/project scale - consistent with the existing in-memory rate limiter (`rateLimiter.ts`) accepting the same class of risk today. |
</threat_model>
